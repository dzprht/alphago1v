# Стек и основания выбора

**Статус: решения согласованы 25 октября 2026 года; реализация с нуля.** Основной стек — **Python 3.11 + Django 5.2 LTS + Django Templates + PostgreSQL 17**. Здесь зафиксирован план, а не факт установки или готовности приложения.

Установлен Django 5.2.18, зависимости зафиксированы в `uv.lock`. Для проверки изображений используется Pillow 12.3.0. Локально работает PostgreSQL 17.11 из ветки `postgres:17`. На 5 ноября проходят 284 тестовых случая основной реализации, включая HTTP аккаунтов, истории, CSV, ручного ввода, отзывов и справочник организаций. DTL подключен с общим base.html, общим выводом полей и одним адаптивным CSS. Небольшой JavaScript добавляет строки ручного ввода; серверный вариант работает без него. Сборщик и новые зависимости не нужны. Для запуска на хостинге добавлен Gunicorn 26.2.0; команда находится в Procfile. GitHub Actions настроен на PostgreSQL 17; результат удаленного запуска проверяется после push.

Актуальные функции F01–F09 описаны в [kharchenko_application.md](kharchenko_application.md) и [SPECIFICATION.md](SPECIFICATION.md), устройство — в [ARCHITECTURE.md](ARCHITECTURE.md). По решению пользователя старый код не переносим; [application_2359.md](application_2359.md) остаётся неизменной исходной копией. Совместимость с прежним проектом не ограничивает выбор технологий.

## Почему модульный монолит

Аккаунты, проверки, CSV и анализ разделены в коде одного Django-проекта. Так проще менять поведение и проверять полный сценарий одному разработчику. Независимое развёртывание модулей пока не даёт нужного выигрыша.

**Монолит, экземпляр приложения и сервер БД — разные понятия.** Монолит описывает организацию кода, экземпляр — запущенную копию приложения, PostgreSQL — отдельный сервер данных. Django и PostgreSQL могут размещаться на разных машинах; наличие одного веб-сервера само по себе не требует SQLite.

По `ProjectGuide` (слайды 12–13) нужно объяснить инструменты и тип БД с учётом времени на освоение. Именно это определяет выбор, а не наличие стека в старом проекте. Основная самостоятельная работа — обработка ситуаций, использование истории, анализ и объяснения; типовую веб-инфраструктуру берём из Django.

## Окружение и воспроизводимость

Целевой рабочий venv: `/Users/Shared/github/MachineLearning/ml_venv`. Его не удаляем и не очищаем от пакетов других проектов. В `pyproject.toml` перечисляем только зависимости «Альфа Защиты», а `uv.lock` фиксирует их разрешённые версии.

Обычный `uv sync` удаляет лишние пакеты из выбранного окружения. Поэтому к общему venv не применяем точную синхронизацию с удалением зависимостей; при настройке явно выбираем целевой путь и проверяем влияние установки. Чистую воспроизводимую установку проверяем в отдельном временном окружении и в CI. [Правила синхронизации uv](https://docs.astral.sh/uv/concepts/projects/sync/).

Версию PostgreSQL и её patch-релиз фиксируем отдельно от Python lock-файла. Локальная БД использует постоянный Docker-том; размещённая — постоянное хранилище провайдера. Для обеих предусмотрены резервное копирование и проверка восстановления. Секреты находятся в окружении, а не в репозитории.

## Проверки и CI

GitHub Actions должен проверять актуальность lock-файла, устанавливать зависимости из него и поднимать **PostgreSQL 17 service**. Затем выполняются системные проверки Django, проверка отсутствующих миграций, применение миграций и `pytest` с `pytest-django`. SQLite для проверки работы БД не подменяет PostgreSQL.

Проверяем доступ владельца, все пять режимов анализа, ошибки распознавания, импорт без частичной замены, сохранение результатов и отдельное исправление отзыва. Реальное качество моделей и время ответа измеряем отдельно от быстрых тестов веб-части. Перед сдачей проверяем установку по инструкции, обновление существующей БД и восстановление копии.

Основания: [pytest-django](https://pytest-django.readthedocs.io/en/latest/), [PostgreSQL service в GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

## Анализ, ASR и OCR

- **RuBERT-tiny2 + семь выходов.** Общая русскоязычная модель для текста, распознанной речи и скриншотов. Отдельно кодирует реплику и контекст. Выбрана по экспериментам; перенос проверен на точных входах. E5/LR оставлены для прежних обучающих команд, сайту веса E5 не нужны.
- **Символьная URL-CNN.** Получает исходные символы адреса, учитывает сочетания, которых нет среди 12 прежних ручных признаков CatBoost. Выбрана по архивному сравнению; не открывает сайты. Доменные правила и справочник работают отдельно.
- **faster-whisper small, CPU/int8.** Готовое распознавание русской речи и времени слов. Не обучаем еще одну модель речи; содержание дальше оценивает тот же RuBERT.
- **Pyannote community-1.** Автоматически разделяет голоса. A/B обозначают разные голоса, но не владельца записи. Локальная загрузка не требует сетевого доступа во время запроса.
- **EasyOCR CRAFT + cyrillic_g2.** Готовые детекция и чтение русского/английского текста. Простой геометрический блок связывает строки с пузырями; неподходящее оформление ограничивает ответ.
- **Стандартный Python для перевода и правил.** Целые копейки и Decimal, Modified Z с порогом 3.5 и минимумом 20 исходящих. Итог собирает warning-rules-v1, обучаемого дерева в веб-запуске нет.
- **tldextract и idna.** Зарегистрированный домен и единая форма Unicode/ASCII без самодельного разбиения по точкам. Обновление PSL по сети отключено.

PyTorch/Transformers находятся в группе ml; медиабиблиотеки — в media. На Linux закреплены CPU-колеса. Группа whisper позволяет отдельно проверить ASR без pyannote и OCR. Все версии — в uv.lock; модели и токенизаторы закреплены и проверяются по хешам. Общие функции работы с файлами весов переиспользуются.

Отдельный risk-классификатор, брокер и очередь не нужны текущей реализации. Один Gunicorn worker переиспользует локальные модели. Nginx завершает HTTPS и передает достоверный IP, systemd отвечает за запуск и перезапуск. WhiteNoise отдает собранные статические файлы через приложение.

Обучение и подготовка весов выполняются отдельно от HTTP. Отзыв не запускает обучение; согласие относится к конкретной проверке. Исходные медиа временные, в аккаунте сохраняется извлеченный текст. Точность распознавания и ресурсы на AdminVPS требуют отдельной проверки на реальных материалах. Настройка — [VPS](docs/VPS.md), точная схема — [ML_PLAN](ML_PLAN.md).
