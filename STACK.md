## Почему модульный монолит

Аккаунты, проверки, CSV и анализ разделены в коде одного Django-проекта. Так проще менять поведение и проверять полный сценарий одному разработчику. Независимое развёртывание модулей пока не даёт нужного выигрыша.

**Монолит, экземпляр приложения и сервер БД — разные понятия.** Монолит описывает организацию кода, экземпляр — запущенную копию приложения, PostgreSQL — отдельный сервер данных. Django и PostgreSQL могут размещаться на разных машинах; наличие одного веб-сервера само по себе не требует SQLite.

По `ProjectGuide` (слайды 12–13) нужно объяснить инструменты и тип БД с учётом времени на освоение. Именно это определяет выбор, а не наличие стека в старом проекте. Основная самостоятельная работа — обработка ситуаций, использование истории, анализ и объяснения; типовую веб-инфраструктуру берём из Django.

## Окружение и воспроизводимость

Целевой рабочий venv: `/Users/Shared/github/MachineLearning/ml_venv`. Его не удаляем и не очищаем от пакетов других проектов. В `pyproject.toml` перечисляем только зависимости «Альфа Защиты», а `uv.lock` фиксирует их разрешённые версии.

Обычный `uv sync` удаляет лишние пакеты из выбранного окружения. Поэтому к общему venv не применяем точную синхронизацию с удалением зависимостей; при настройке явно выбираем целевой путь и проверяем влияние установки. Чистую воспроизводимую установку проверяем в отдельном временном окружении и в CI. [Правила синхронизации uv](https://docs.astral.sh/uv/concepts/projects/sync/).

Версию PostgreSQL и её patch-релиз фиксируем отдельно от Python lock-файла. Локальная БД использует постоянный Docker-том; размещённая — постоянное хранилище провайдера. Для обеих предусмотрены резервное копирование и проверка восстановления. Секреты находятся в окружении, а не в репозитории.

## Проверки и CI

GitHub Actions должен проверять актуальность lock-файла, устанавливать зависимости из него и поднимать **PostgreSQL 17 service**. Затем выполняются системные проверки Django, проверка отсутствующих миграций, применение миграций и `pytest` с `pytest-django`. SQLite для проверки работы БД не подменяет PostgreSQL.

Проверяем доступ владельца, все пять режимов анализа, ошибки распознавания, импорт без частичной замены, сохранение результатов и отдельное исправление отзыва. Реальное качество моделей и время ответа измеряем отдельно от быстрых тестов веб-части. Перед сдачей проверяем установку по инструкции, обновление существующей БД и восстановление копии.

Основания: [pytest-django](https://pytest-django.readthedocs.io/en/latest/), [PostgreSQL service в GitHub Actions](https://docs.github.com/en/actions/tutorials/use-containerized-services/create-postgresql-service-containers).

## Анализ, ASR и OCR

Пять пользовательских способов проверки не требуют пяти отдельных моделей. Аудио преобразуется в текст через ASR, скриншот — через OCR; далее используется общий текстовый анализ. URL проверяется без посещения адреса. Перевод оценивается по введённым обстоятельствам и доступной прошлой истории.

Библиотеки и модели выбираем после сравнения качества на русскоязычных примерах, времени ответа, памяти и ограничений размещения. Обучение выполняется отдельно от веб-запросов; сайт использует подготовленные версии. Пользовательский отзыв не запускает обучение, данные проверки для будущего обучения требуют отдельного добровольного согласия. Исходные аудио и изображения временные, сохраняется извлечённый текст.

Очередь задач, брокер и отдельные workers не входят в согласованный стек. Сначала измеряем допустимые входы и ресурсы; дополнительную инфраструктуру обсуждаем только при выявленной необходимости.
